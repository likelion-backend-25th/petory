## 1. 간식 쏘기를 누르면 "입력값 검증에 실패했습니다"가 뜬다

### 상황
- 프로필 화면에서 간식 쏘기 모달을 열고 결제 버튼을 누르면, 결제창이 뜨기 전에 `입력값 검증에 실패했습니다.` 메시지가 나왔다.
- 같은 시기에 팔로우 취소 버튼도 동작하지 않았다.

### 처음 의심한 것
- 금액이나 후원 대상 id가 잘못 들어간 줄 알고 프론트의 금액 입력 부분부터 봤다. 그런데 금액은 정상이었다.

### 원인
에러 응답 본문의 `errors` 배열을 열어보고 나서야 원인이 보였다. 이 메시지는 `@Valid` 검증에 실패했을 때 공통으로 나오는 문구라서, **어떤 필드가 틀렸는지는 `errors`를 봐야** 알 수 있었다.

```json
{
  "code": "INVALID_INPUT_VALUE",
  "message": "입력값 검증에 실패했습니다.",
  "errors": [
    { "field": "merchandise", "rejectedValue": "", "reason": "결제 상품은 필수입니다." }
  ]
}
```

- 결제 준비 API의 요청 필드를 `payMethod`에서 `merchandise`로 바꿨다. 결제 수단(카드 등)이 아니라 결제 상품(간식 쏘기 / 구독)을 받는 값이었기 때문이다.
- 그런데 브라우저에는 바꾸기 전 화면이 열려 있어서, 여전히 `payMethod`를 보내고 있었다. 서버 입장에서는 `merchandise`가 비어 있으니 400을 돌려줬다.
- 팔로우 취소도 같은 종류의 문제였다. 프론트는 `DELETE /follow`로 호출하는데 백엔드에는 `POST /follow`(토글)만 있었다.

```java
@NotBlank(message = "결제 상품은 필수입니다.")
@Pattern(regexp = "singlePayment|automaticPayment", message = "결제 상품은 singlePayment 또는 automaticPayment만 가능합니다.")
String merchandise      // 결제 상품 (singlePayment: 간식 쏘기, automaticPayment: 구독하기)
```

### 해결
- 프론트 담당자와 필드명과 허용 값(`singlePayment`, `automaticPayment`)을 다시 맞추고, 새로고침해서 최신 화면으로 확인했다.
- 팔로우 취소는 프론트 호출 방식에 맞춰 `DELETE /api/v1/profile/{memberId}/follow`를 추가했다. 내부 동작은 기존 토글과 같다.

### 배운 점
- 400이 나면 `message`만 보지 말고 **`errors` 배열부터 확인**한다. 어떤 필드가 왜 틀렸는지 거기 다 적혀 있다.
- 요청 필드 이름을 바꾸는 건 프론트와의 약속을 바꾸는 일이다. 바꾸기 전에 먼저 공유하고, API 명세(`docs/02_design/04_api_specification.md`)와 Bruno 요청 파일도 같이 고쳐야 한다.

### 남은 과제
- 코드리뷰에서 "DB의 `pay_method` 컬럼에 결제 수단이 아니라 결제 상품이 들어간다"는 지적을 받았다. 요청 필드 이름만 바꾸고 컬럼 이름은 그대로 둬서 생긴 문제다. 컬럼 이름을 `merchandise`로 바꾸거나, 결제 수단은 PortOne 응답의 `method` 값으로 따로 저장하는 방향을 정해야 한다.

## 2. 로그인 없이 써야 하는 API가 401을 돌려준다

### 상황
- 회원가입 화면의 이메일/닉네임 중복 확인 버튼을 누르면 401(`인증이 필요하거나 유효하지 않은 자격 증명입니다.`)이 나왔다.
- 로그인하지 않은 상태로 다른 사람 프로필에 들어가도 같은 401이 나왔다.

### 처음 의심한 것
- 프론트에서 토큰을 잘못 보내는 줄 알았다. 하지만 회원가입 전이라 애초에 토큰이 있을 수가 없었다.
- 컨트롤러에 로그를 찍어 봤는데 아무것도 찍히지 않았다. 요청이 컨트롤러까지 오지도 않는다는 뜻이었다.

### 원인
- Spring Security 필터는 **컨트롤러보다 먼저** 실행된다. `SecurityConfig`에 `permitAll()`로 열어 두지 않은 경로는 토큰이 없으면 필터에서 바로 401로 끝난다.
- 중복 확인 API와 프로필 조회 API를 만들면서 `SecurityConfig`에 경로를 추가하지 않았다.
- 서버에 아직 배포되지 않은(존재하지 않는) 경로를 호출해도 404가 아니라 401이 나온다. 이 점 때문에 "배포가 안 된 건지, 권한 문제인지" 헷갈렸다.

### 해결
로그인 없이 써야 하는 GET 요청만 골라서 열었다.

```java
// 회원가입과 가입 전 중복 확인
.requestMatchers("/api/v1/signup").permitAll()
.requestMatchers(HttpMethod.GET, "/api/v1/email/exists", "/api/v1/nickname/exists").permitAll()

// 프로필 조회는 비로그인도 가능
.requestMatchers(HttpMethod.GET, "/api/v1/profile/*", "/api/v1/profile/*/posts").permitAll()
```

- `HttpMethod.GET`을 붙여서 조회만 열고, 같은 경로의 수정·삭제 요청은 계속 인증이 필요하게 했다.

### 배운 점
- 새 API를 만들면 "로그인 없이 호출되는가?"를 먼저 생각하고, 그렇다면 `SecurityConfig`도 같이 수정한다.
- 401이 나는데 컨트롤러 로그가 없으면 Security 설정부터 본다.

### 남은 과제
- 가입 시 중복을 다시 검사해서 `DuplicateResourceException`을 던지는데, `GlobalRestExceptionHandler`에 이 예외 전용 처리가 없다. 그래서 마지막 `Exception` 처리로 넘어가 500이 나간다. 409(Conflict)로 응답하는 처리를 추가해야 한다.

## 3. 프론트가 보낸 결제 금액을 믿어도 될까

### 상황
- 간식 쏘기는 프론트에서 금액을 정해서 PortOne 결제창을 띄운다.
- 개발자 도구로 금액을 바꾸면 5,000원짜리를 100원에 결제하고도 "결제 완료"가 될 수 있다는 걸 알게 됐다.

### 처음 생각한 방법
- 결제가 끝나면 프론트가 `/complete`로 금액을 같이 보내고, 서버는 그 금액을 저장하면 된다고 생각했다.
- 하지만 그 금액도 프론트가 보내는 값이라 똑같이 조작할 수 있다.

### 해결
"프론트가 보낸 값은 믿지 않는다"를 기준으로 3단계로 나눴다.

1. **결제 전(`/prepare`)**: 서버가 주문번호를 만들고, 결제할 금액을 `payment` 테이블에 `READY` 상태로 먼저 저장한다.
2. **결제창**: 프론트는 서버가 준 주문번호로 PortOne 결제를 진행한다.
3. **결제 후(`/complete`)**: 프론트는 주문번호만 보낸다. 서버가 PortOne API로 실제 결제 내역을 직접 조회해서, **DB에 저장해 둔 금액과 실제 결제 금액을 비교**한다.

```java
Integer expectedAmount = payment.getTotalAmount();              // 결제 전에 DB에 저장한 금액
Integer actualPaidAmount = portOnePayment.amount().total();     // PortOne이 알려준 실제 결제 금액

if (!expectedAmount.equals(actualPaidAmount)) {
    // 금액이 다르면 위변조로 보고 자동 취소한다
    return handleAmountMismatch(payment, actualPaidAmount);
}
```

- 금액이 다르면 PortOne 취소 API를 호출해서 돈을 돌려주고, `payment`는 `CANCELLED`, `cancel_payment`에는 취소 이력을 남긴다.
- PortOne이 주는 시각은 `2026-09-28T04:00:00Z`처럼 UTC 기준이다. 그대로 저장하면 9시간 차이가 나서 `toKoreanTime()`으로 한국 시간으로 바꿔 저장한다.

### 배운 점
- 결제처럼 돈이 걸린 값은 **서버가 직접 정하고, 서버가 직접 확인**해야 한다.
- 외부 API 응답의 시간대(UTC/KST)를 항상 확인한다.

## 4. /complete와 웹훅이 동시에 오면 결제가 두 번 처리될까

### 상황
- 결제가 끝나면 프론트가 `/complete`를 호출한다. 그런데 사용자가 결제 직후 창을 닫으면 `/complete`가 안 올 수 있다.
- 그래서 PortOne 웹훅(`/api/v1/payments/webhook`)도 받기로 했다. 그러자 **같은 결제에 대해 `/complete`와 웹훅이 거의 동시에 올 수 있다**는 문제가 생겼다.
- 둘 다 `READY`를 읽고 둘 다 `PAID`로 바꾸면, 결제 처리가 두 번 된다.

### 처음 생각한 방법
- "이미 PAID면 건너뛴다"는 `if`문 하나로 충분하다고 생각했다.
- 하지만 두 요청이 동시에 `READY`를 읽으면 둘 다 `if`를 통과한다. 조회와 변경 사이에 틈이 있었다.

### 해결
세 겹으로 막았다.

1. **행 잠금**: 결제를 조회할 때 `SELECT ... FOR UPDATE`로 그 행을 잠근다. 뒤에 온 요청은 앞의 트랜잭션이 끝날 때까지 기다린다.
2. **상태 확인**: 기다렸다가 읽으면 이미 `PAID`라서, PortOne을 다시 호출하지 않고 현재 상태만 돌려준다.
3. **조건부 UPDATE**: 혹시 모르니 UPDATE에도 `AND status = 'READY'`를 붙여서 `READY`일 때만 바뀌게 했다.

```xml
UPDATE payment
SET status = 'PAID', ...
WHERE payment_id = #{paymentId}
  AND status = 'READY'
```

- `/complete`와 웹훅이 같은 메서드(`syncWithPortOne`)를 쓰도록 합쳐서, 어느 쪽이 먼저 와도 결과가 같게 했다.
- 웹훅 URL은 누구나 호출할 수 있으므로 웹훅 본문 내용은 믿지 않는다. 본문에서는 주문번호만 꺼내고, 실제 상태는 PortOne API로 다시 조회한다.
- DB에 없는 주문번호로 웹훅이 오면 예외를 던지지 않고 200으로 끝낸다. 에러를 돌려주면 PortOne이 같은 웹훅을 계속 다시 보내기 때문이다.

### 배운 점
- "확인하고 바꾸기"를 두 번의 쿼리로 나누면 그 사이에 다른 요청이 끼어들 수 있다. 잠금이나 조건부 UPDATE로 틈을 없애야 한다.
- 같은 일을 하는 경로가 두 개면 로직을 하나로 합쳐야 결과가 어긋나지 않는다.

## 5. 해시태그 검색에 엉뚱한 글이 나오거나 있어야 할 글이 안 나온다

### 상황
- `강아지`로 검색하면 `#강아지간식` 글까지 나왔다.
- `#산책 #강아지`처럼 **마지막에 붙은 태그**로는 검색이 안 됐다.
- 프론트에서 `?hashtag=#강아지`로 요청하면 결과가 하나도 없었다.

### 처음 시도한 것
```sql
WHERE hashtags LIKE '%강아지%'
```
- 글자가 포함만 되면 다 걸려서 `#강아지간식`, `#큰강아지`도 나왔다.
- 멘토님께 여쭤봤을 때 `=`은 정확히 일치할 때, `LIKE`는 일부만 맞아도 될 때 쓴다는 설명을 들었다. 지금은 태그 여러 개가 한 컬럼에 문자열로 들어 있어서 `=`은 쓸 수 없고, `LIKE`의 범위를 좁혀야 했다.

### 원인
- 해시태그는 별도 테이블 없이 `post_main.hashtags` 컬럼에 `'#강아지 #산책 #한강'`처럼 문자열로 저장된다.
- 태그의 **앞쪽 경계는 `#`**, **뒤쪽 경계는 공백**인데, 마지막 태그 뒤에는 공백이 없다.
- URL에서 `#`은 프래그먼트 시작 기호라서, 브라우저가 `#` 뒤를 서버로 보내지 않는다. 서버는 빈 문자열을 받았다.

### 해결
```sql
WHERE CONCAT(hashtags, ' ') LIKE CONCAT('%#', #{hashtag}, ' %')
```

- 컬럼 끝에 공백을 하나 붙여서 마지막 태그 뒤에도 공백이 오게 만들었다.
- `#`을 앞 경계, 공백을 뒤 경계로 써서 태그 하나를 정확히 찾는다.
- 서버에서 검색어 앞의 `#`을 떼어내고, 프론트에는 `#` 없이 보내거나 `%23`으로 인코딩해서 보내 달라고 요청했다.
- `'%${hashtag}%'`는 SQL 인젝션 위험이 있어서 `#{}`와 `CONCAT`을 썼다.

### 배운 점
- `LIKE` 검색은 "어디까지가 한 단어인지" 경계를 직접 만들어 줘야 한다.
- 검색 쿼리는 저장 형식(`#태그` + 공백 구분)에 기대고 있다. 그래서 `#` 없이 저장된 글은 검색되지 않는다. 형식을 지키는 것이 중요하다.

### 남은 과제
- 앞에 `%`가 붙은 `LIKE`는 인덱스를 쓰지 못해 게시글 전체를 훑는다. 지금 데이터 양에서는 괜찮지만, 글이 많아지면 `hashtag`, `post_hashtag` 테이블로 분리해야 한다.
- 게시글 작성 시 서버에서 해시태그 형식을 정리해서 저장하면 프론트 실수에도 검색이 안전해진다.

자세한 내용은 [해시태그 검색 스터디](../04_study/hashtag_search.md)에 정리했다.

## 6. 10개를 요청했는데 게시글이 몇 개만 온다

### 상황
- 해시태그 검색에서 `size=10`으로 요청했는데 게시글이 3~4개만 왔다.
- 다음 페이지가 있는데도 `hasNext`가 `false`로 오는 경우가 있었다.

### 처음 의심한 것
- 커서(`lastPostId`) 조건이 잘못된 줄 알고 `WHERE id < #{lastPostId}` 부분만 계속 봤다.

### 원인
- 게시글과 이미지를 `LEFT JOIN`하면 이미지 수만큼 행이 늘어난다. 이미지 3장인 게시글은 3행이 된다.
- 그 상태에서 `LIMIT 11`을 걸면 **게시글 11개가 아니라 행 11개**를 가져온다.
- MyBatis `<collection>`이 같은 게시글끼리 묶고 나면 게시글 수가 요청보다 적어진다.

### 해결
게시글을 먼저 서브쿼리에서 잘라 놓고, 그다음에 이미지를 붙였다.

```sql
FROM (
    SELECT *
    FROM post_main
    WHERE type = 1
    AND CONCAT(hashtags, ' ') LIKE CONCAT('%#', #{hashtag}, ' %')
    ORDER BY id DESC
    LIMIT #{limit}          -- 게시글 기준으로 자른다
) p
INNER JOIN member m ON p.member_id = m.id
LEFT JOIN post_image img ON p.id = img.post_id
```

### 배운 점
- 1:N JOIN 뒤에 `LIMIT`을 걸면 기준이 "행"이 된다. 페이지 크기를 "부모 개수"로 맞추려면 부모를 먼저 잘라야 한다.
- 테스트 데이터에 이미지가 1장씩만 있으면 이 문제가 안 보인다. 더미 데이터에 이미지 여러 장짜리 게시글을 넣어 두는 것이 좋다.

### 남은 과제
- 메인 피드 쿼리(`selectPostListCursor`)는 아직 JOIN 뒤에 `LIMIT`을 거는 구조라 같은 문제가 남아 있다. 해시태그 검색과 같은 서브쿼리 방식으로 바꿔야 한다.
